# 方案 A（segment/associative-scan）评估：数学成立，但成本不成立

日期：2026-09-20。对象：把 K2 的串行 chunk 递推改造成"段内计算 + 段级前缀 + 修正输出"
的三趟结构（seg = 4/8/16）。结论先行：**第 1 步（数学等价）成立，且原方案第 6 步有一处
O(1) 偏差需要修正；但第 2 步的判决性实验证明这台机器是吞吐受限、不是串行链受限，而
第 4 步的成本地板实测表明 pass 1 一项就超过整个 K2 阶段——所以按原样实施不应进行。**

下面每个数字都可用仓库内脚本复现，脚本路径随行给出。

## 1. 数学形式：成立（`tools/probe_segment_affine.py`，CPU）

约定取仓库自己的 `state_v_first=True`，状态 `h = [V, K]`，`chunk_fwd` 的递推是

```
v_new  = u - w @ S^T
S_out  = S * d[None,:] + v_new^T @ kg      d = exp2(g_last)
o      = scale * (qg @ S^T) + Aqk @ v_new
```

代入即得仿射形式（fp64 复核误差 3.5e-18）：

```
S_out = M @ S_in + Q,     M = diag(d) - w^T @ kg,     Q = u^T @ kg
o     = Aqk @ u + R @ S_in^T,  R = scale*qg - Aqk @ w
```

段复合（NT=32 全串复核误差 6.9e-18）：

```
M_seg = M_1 M_2 ... M_s          Q_seg = Σ_j Q_j (M_{j+1} ... M_s)
```

**省事的一步**：`h = I` 跑一遍再减去 `h = 0` 那遍，直接得到 `M_seg`（误差 1.4e-06，
即 fp32 舍入量级），所以 pass 1 不需要显式矩阵乘法，用现有 chunk 数学即可产出
`M_seg`/`Q_seg`。

## 2. 原方案第 6 步的修正（否则输出误差 O(1)）

原文 `O_i = Q_i + R_i(S_in,i)` 里的 `S_in,i` 是**段**输入状态，而 chunk i 的真实输入
状态是 `S_i = S_in[j] M_{j→i−1} + Q_{j→i−1}`。实测按原式实现的输出相对误差 **4.8e-01
～ 6.2e-01**（seg=4/8/16）。正确形式把段内那一半也补上：

```
o_i = [Aqk_i u_i + R_i Q_{j→i−1}^T]  +  [R_i M_{j→i−1}^T] S_in[j]^T
      ↑ pass 1 顺便得到（Q_{j→i−1} = S0 进位，M_{j→i−1} = S1 − S0）
```

修正后输出相对误差 **2.9e-05**（与状态误差 3.7e-05 同量级），且 pass 3 变为每 chunk 一次
matmul、**无状态、无串行链**——这正是整条路线想要的性质。

## 3. 基线（`KDA_CHUNK=64`，B=1，T=8192，H=96，MIN of 3）

| 项 | 值 |
|---|---:|
| e2e wall | 15.2–18.9 ms（随机器负载波动） |
| pre_gram | 4.38 ms |
| solve | 2.50 ms |
| **k2** | **4.20 ms** |
| K2 单 head 全链（H=1，nblk=1，128 步） | 1.03 ms（8.07 µs/步） |

串行链长度 = NT = 128（C=64）；一个 head 的链成本 = 1.03 ms。

## 4. 判决性实验：吞吐受限，不是串行链受限

**A. 固定 T（链长恒为 128），扫 H**（同一入口 `kda_bt16_fwd_ascendc` + `KDA_PROFILE=1`，
两个独立进程各测一轮，取其中值一致的一组）：

| H | heads/block | k2 (ms) | 每步（全 block，µs） | 每 head-步（µs） |
|---|---:|---:|---:|---:|
| 24 | 1 | 1.99 | 15.5 | 15.5 |
| 48 | 2 | 2.21 | 17.2 | 8.6 |
| 96 | 4 | 4.20 | 32.8 | 8.2 |

链长三个点完全相同（都是 128 步）。1x/2x/4x 工作量给出 1x/1.11x/2.11x 时间：每 head-步
从 15.5 µs 降到 8.2 µs，说明机器本来就有并行余量；但 4x 工作量只换来 2.11x，说明 H=96
时已接近饱和。注意 `t = L + w·heads` 这一定价模型在 H=96 上并不成立（H=24/48 两点给
`w ≈ 0.01 ms/head`，外推 H=96 应得 ~2.6 ms，实测 4.20）——**它失效的方向恰好是对 route A
不利的方向**：高占用下头间会互相争资源。这与 §11.17 的结论一致（两条半流水并发 =
一条整流水 8.93 ms）。

**B. 同等工作量、不同链长**（`B·T` 固定的头-token 数，H=96）：

| 配置 | NT（链长） | nblk | k2 (ms) |
|---|---:|---:|---:|
| B=1, T=8192 | 128 | 24 | 4.24 |
| B=4, T=2048 | 32 | 96 | 2.88 |
| B=8, T=1024 | 16 | 192 | 2.96 |

这是对 route A 最有利的读数：把链长砍到 1/8（并发链从 24 条变 192 条）只省
**1.28–1.36 ms**。**这就是"链"在整机上的全部可回收成本，也正是 route A 收益的上界。**

## 5. 成本地板：pass 1 一项就超过整个 K2（`tools/probe_segment_floor.py`）

把每个 (head, segment) 当作独立批行（这正是 kernel 能拿到的并行度），pass 1 的 8 个
串行步全部合批到 96 head × 16 段 = 1536 行上，实测量级：

| seg | pass 1 (ms) | pass 3 (ms) | 合计 | 对比 k2 = 4.20 ms |
|---|---:|---:|---:|---:|
| 4 | 16.7 | 5.5 | 22.2 | 5.3x |
| 8 | 14.1 | 5.0 | 19.2 | 4.6x |
| 16 | 10.7 | 4.8 | 15.5 | 3.7x |

先看与探针实现无关的**强制流量**（结构性的，不看探针数字也成立）：

- **状态工作集变成 `heads × segments`，必须绕 GM。** 原设计里状态每 head 一份、常驻
  UB（bf16 每子核 64×128）；route A 里每个 (head, segment) 要同时维护 `S0`/`S1` 两份
  128×128 fp32 = 128 KB。seg=8 时是 96×16 = 1536 行 × 128 KB = **每份进位 201 MB**，
  24 块 × 192 KB UB 一份都放不下，**只能每步绕一圈 GM**：8 步 × 读+写 = **3.2 GB**。
  按机器实测的 ~1.1 TB/s 拷贝带宽，**光这一项约 2.9 ms** —— 已经是全部可回收收益
  （1.2–1.3 ms）的 2.2 倍，也接近整个 K2 阶段（4.2 ms）的 70%。
- pass 3 另要一整趟 `[12288, 64, 128] × [12288, 128, 128]` 的 matmul（≈26 GFLOP）外加
  `S_in` 的读取，量级与上一条相当。
- 探针的 torch 实现（10.7–16.7 ms）是这些结构性成本的上界（含 host 逐 op 开销），它
  与上面的流量估算（~2.9 ms 强制、若算力允许）同向：**没有任何一种读法能让 pass 1 低到
  1.2 ms 以下**，而这已经是 route A 的全部预算。

即：route A 拿"消灭串行链"的全部收益（上界 1.2–1.3 ms，第 4 节）去换"3.2 GB 强制
GM 流量 + 每 chunk 一次新 matmul"。在这台已到吞吐地板的机器上不成立。

## 6. 建议

- **不要**按原样实现三趟结构。数学部分（含第 2 节的修正、`h=I` 取 `M_seg` 的技巧）
  已存档，可直接复用于将来任何"段并行"尝试。
- 若仍要拿串行链的收益，需要的是**不物化 `M_seg`** 的方案：让段内状态进位保持在
  UB 常驻（即维持"每 head 一份状态"），也就是放弃 associative-scan 的段并行，改为
  在现有 persistent_loop 上继续压 per-chunk 成本。这与 §11.17 的结论（唯一出路是
  "少算 40%"级的算法/精度改动）一致。
- 若以后换到更大 UB 或更小 D 的形状（例如 D=64：状态 16 KB/份、段工作集降 4x），
  本评估的结论需要重测，届时应先跑 `tools/probe_segment_floor.py`。

